# GLM-5.3 W4A8 Stage B/C Design

## Goal

Create an isolated GLM-5.3 W4A8 pipeline that reuses the validated Stage B
hidden extraction and Stage C DSpark/DFlash2 training logic without allowing
W8A8 trajectories, target-I/O artifacts, or hidden caches to be mixed in.

## Architecture

`glm-5.3-w4` is a self-contained copy of the current GLM-5.3 W8A8 Stage B/C
pipeline with a separate Python package (`glm53_w4`). The target checkpoint is
validated from `quant_model_description.json` as W4A8, while the target
embedding and language-model head are exported as dense BF16 tensors for Stage
C. Stage B replays exact Stage-A token IDs through vLLM-Ascend's
`extract_hidden_states` interface. Stage C loads only the BF16 target I/O and
hidden cache, so it does not load the full quantized target model.

## Contract

- Target architecture and dimensions remain the formal GLM-5.3 contract.
- Required target hidden layers are `[1, 20, 38, 56, 75]`; raw final layer 78
  is extracted for final normalization and lm-head supervision.
- Target quantization must be explicitly W4A8. W8A8, W4A8C8, FP8, and unknown
  metadata are rejected.
- Target I/O artifacts use `formal-glm53-w4a8-target-io-v2` and contain dense
  BF16 `embed_tokens.weight` and `lm_head.weight`.
- Hidden caches use `formal-glm53-w4a8-hidden-cache-v2` and record the target
  quantization, runtime backend, model fingerprint, tokenizer fingerprint,
  layer IDs, and trajectory checksum.
- Physical sliding-window attention remains 2048 tokens with the same left
  context halo and block-tail semantics as W8A8.
- DSpark is B8 only; DFlash2 supports B8 and B16.

## Runtime boundary

The vLLM-Ascend engine still receives `quantization=ascend`; the actual W4A8
ABI is selected by the ModelSlim checkpoint metadata. The code can validate the
artifact and launch Stage B, but only a 910B vendor environment can establish
that the installed vLLM-Ascend build supports GLM-5.3 W4A8 hidden extraction.
The first hardware gate is a one-sample, teacher-forced replay.

## Data flow and safety

1. Stage A is external and must generate trajectories with the exact W4A8
   target. Its sidecar records W4A8 and the model/tokenizer fingerprints.
2. Stage B validates that sidecar, replays the exact token IDs, and writes
   BF16 auxiliary/final hidden states into a resumable W4A8 cache.
3. Stage C validates matching W4A8 provenance and trains BF16 DSpark or
   DFlash2. It never silently dequantizes or substitutes a W8A8 artifact.

If the W4A8 checkpoint quantizes the embedding or lm-head, a dense BF16 copy
of those two tensors must be supplied separately; the exporter fails closed
rather than dequantizing without an explicit calibration contract.

## Verification

The CPU tests cover W4A8 acceptance, rejection of other quantization types,
manifest/cache mismatch, exact token alignment, physical windows, finite
losses, and launcher syntax. `compileall` and `bash -n` are also required.
The NPU smoke must additionally confirm W4A8 model loading, six hidden streams,
BF16 dtype, exact token IDs, and one finite Stage-C optimizer step.
